## Screen auto-detection researched

Reconnaissance ahead of a possible "guess my screen size" onboarding
feature — no code changed. `getScreenDetails()` never returns physical
mm/inches on any engine, and it's Chromium-only with Firefox and
WebKit standards-positions issues still open (WebKit's flagged
`concerns: privacy`/`concerns: annoyance` since 2022). Resolution can
pin the exact device for Apple laptops/desktops/displays, the Switch
family, Steam Deck, and common phones/tablets, but is a wide, unreliable
guess for ordinary desktop monitors at 1080p/1440p/4K. Also found a
real gap: the repo's `dpr * screen.width / resolution.w` zoom-detection
trick (`calibration-dialog.tsx`, `display-area.tsx`, `scene-view.tsx`)
relies on Chrome/Safari freezing `screen.width` at 100%-zoom CSS px;
Firefox recomputes it live so the product is zoom-*invariant* there by
design (confirmed via a Mozilla engineer's comment on a still-open
Bugzilla issue) — the zoom warning would never fire in Firefox.

- created [[screen-auto-detection]] — full findings, resolution→device
  table, and the recommendation: confirm-not-silent prefill for
  device-exact matches, no prefill for ordinary monitors, calibration
  stays primary either way.

## OCR cost measured ahead of auto-scan

Benchmarked the real vendored Tesseract.js runtime (not guessed) before
committing to auto-scan-on-import for #2: ~1.5s cold start once per
session, under 400ms warm at any tested resolution, main thread never
stalls (worker-based). Confirmed the local-only promise holds — every
worker/core/traineddata path is vendored under `public/ocr/`, verified
both by source and by watching the network panel during live scans; no
CDN call anywhere. Scan results already cache per item in IndexedDB
today. Recommendation: fire on import with no debounce (the existing
single-flight lock already serializes a batch), and ship the seeded
gradient card's OCR detections as precomputed static data (measured:
1505 bytes) rather than scanning it at boot.

- created [[ocr-cost]] — full pipeline notes, the cost table, and the
  auto-scan recommendation.

## The Firefox zoom bug is real, and it constrains more than the warning

Verified by measurement rather than by citation: a probe page driven through
each browser's own zoom UI on the same 5120×1440 panel. Firefox keeps
`screen.width × devicePixelRatio` pinned at 5120 across 50/70/100/140% zoom
— 0.01% deviation, nowhere near the app's 2% threshold — so the warning
cannot fire there at any zoom level. Chrome scales the product linearly and
the check works as designed. `visualViewport.scale` reads exactly 1 in both
engines, so it is not the fallback.

The part worth remembering is the knock-on: [[issue #10]], scaling the UI
while the content holds its physical size, needs the zoom factor as a
NUMBER. Firefox doesn't expose the second independent quantity Chrome's
trick depends on — `devicePixelRatio` folds OS scale and zoom together in
both engines, and only Chrome leaves `screen.width` frozen to divide them
apart. So compensation is buildable where zoom is measurable and must
degrade honestly where it isn't. Guessing the factor would produce
confidently wrong physical sizes, which is worse than the warning it
replaces.
